1. Cek harian: dua perintah

Buka Terminal di Mac, lalu masuk ke VPS:

ssh -o StrictHostKeyChecking=yes -o ServerAliveInterval=30 ubuntu@43.157.242.8

Tunggu sampai prompt menjadi ubuntu@VM-11-154-ubuntu, lalu jalankan:

sudo /usr/local/sbin/sinegasi-monitor report

SSH sekarang memakai key. Jika muncul Enter passphrase for key, gunakan passphrase SSH key jika Anda memasangnya. Dialog macOS Keychain meminta password login Mac. Prompt [sudo] password for ubuntu meminta password akun VPS, bukan password backup/database/R2. Jangan mengirim password ke chat. Jika host key berubah, berhenti dan verifikasi.

2. Cara membaca laporannya

BagianYang perlu dilihat
LayananAKTIF untuk Docker, cron, SSH, dan Tunnel. Container healthy hanya membuktikan proses merespons, bukan seluruh fungsi/DB sehat.
Sumber dayaPerhatikan kenaikan RAM/disk/restart. Beban CPU 1 menit bukan persen CPU. Disk >80% layak diperiksa; jangan langsung menghapus data.
CollectorWaktu terbaru seharusnya terus maju; segar ≤15 menit. BELUM TERKONFIRMASI, batas tercapai, atau gap bukan kondisi sehat/nol.
API dan errorHit non-health terpisah dari health check. 401: sesi/login tidak valid; 403: akses ditolak; 429: dibatasi; 5xx: masalah server/dependensi. Satu kejadian tidak membuktikan serangan.
Aktivitas akunSesudah rilis aplikasi baru: UUID akun terverifikasi dengan aktivitas ≤10 menit, bukan daftar orang pasti online.
SSHGagal password/invalid user merupakan kejadian jurnal, bukan orang unik. Histori 24 jam bisa memuat kejadian sebelum hardening. Cocokkan waktu login sukses dengan aktivitas admin; angka nol bukan jaminan tidak ada serangan.
BackupCari jadwal aktif, tidak terlambat, upload terverifikasi. Bukti upload bukan bukti restore berhasil. Lihat laporan khusus backup untuk rincian.

Semua waktu ringkasan adalah WIB. Exit 0 pada perintah laporan berarti laporan berhasil ditampilkan, bukan sertifikat seluruh aplikasi aman.

Contoh dummy — bukan hasil pemeriksaan live

Collector terakhir : 20-10-2026 09:03:01 WIB
API error tercatat : 3 status 5xx; 8 status 401; 2 status 429
Error terbaru      : 20-10-2026 09:01:12 WIB | /api/grades/* | HTTP_5XX

Mulai pemeriksaan modul nilai sekitar 09.01 WIB: tiga respons server error bukan tiga orang menyerang. 401/429 dapat berasal dari sesi kedaluwarsa atau limiter. Format aktual dapat berbeda; jangan mengetik baris laporan sebagai perintah.

3. Bukti jadwal dan lokasi data

sudo bash /usr/local/lib/sinegasi-monitor-v1/control-vps.sh status

Harapkan MONITOR_CRON_ENABLED, lalu cocokkan waktu collector pada laporan. Monitor berjalan semua hari, tiap 5 menit: menit 03, 08, 13, 18, 23, 28, 33, 38, 43, 48, 53, 58. Jadwal ini berbeda dari backup database.

  • Jadwal monitor: /etc/cron.d/sinegasi-monitor.
  • State ringkasan privat: /var/lib/sinegasi-monitor/state.json, hanya root. Gunakan perintah laporan; tidak perlu membuka JSON mentah.
  • Retensi maksimal 14 hari, 20.000 event, 15 MiB; batas kapasitas dapat membuang data lebih cepat. Ini subset, bukan arsip bukti lengkap.
  • Setiap koleksi maksimal satu jam ke belakang/5.000 baris Docker. SSH maksimal 10.000 baris jurnal/24 jam. Rotasi, trafik tinggi, atau jeda dapat membuat celah.

Untuk rincian keberhasilan, waktu/tahap kegagalan dan objek backup yang tercatat:

sudo /usr/local/sbin/sinegasi-backup report

Panduan backup terpisah yang sebelumnya dibuat berada di Mac, bila tersedia: ops/scheduled-backup/Panduan-Cek-Cron-Backup-Sinegasi.pdf.

4. Cloudflare: hit, bot, dan alert

  1. Buka Cloudflare Dashboard → domain sinegasi.pictures → Analytics/Traffic. Pisahkan hostname frontend dan api.sinegasi.pictures; bandingkan satu jam dengan 24 jam.
  2. Pilih Last 1 hour untuk insiden baru, atau Last 24 hours untuk harian. Tambahkan filter Hostname → equals/is → api.sinegasi.pictures → Apply. Jika label berbeda, cari Security Analytics pada pencarian dashboard.
  3. Buka Security/Analytics → Events. Filter Action = Block, lalu periksa Managed Challenge secara terpisah bila UI tidak mendukung beberapa nilai. Klik satu baris: baca waktu, hostname/path, action, rule/service dan Ray ID. Jangan menyebarkan ekspor mentah.
  4. Di tingkat akun → Alerts → Overview (label lama: Notifications), cari Sinegasi PROD - Tunnel Health dan Sinegasi - HTTP DDoS. Keduanya enabled dan memakai email admin budget alert yang sudah terdaftar. Alert Tunnel difilter ke tunnel produksi; DDoS berlaku tingkat akun.
  5. Pada tiap alert klik ⋯ → Test bila tersedia, lalu periksa Inbox/Spam pada email tujuan yang sudah terdaftar. Catat jam dan apakah diterima; jangan mengirim alamat email/token ke chat. Test memakai contoh alert: jangan mematikan Tunnel atau membuat DDoS untuk mencoba.
  6. Tingkat akun → Networking → Tunnels → sinegasi-prod-api: periksa Healthy/Degraded/Down. Jangan tertukar dengan Cloudflare WAN/GRE/IPsec. Tunnel healthy belum membuktikan API/database sehat.

Request yang diblokir di Cloudflare tidak mencapai VPS. Hit bukan jumlah orang; data Events pada paket Free berupa sampel. DDoS alert mempunyai ambang, bukan pemberitahuan semua bot. Pembayaran domain berbeda dari paket keamanan website; zone saat diperiksa memakai Free Website. Tidak ada paket baru yang dibeli.

Navigasi merujuk dokumentasi resmi Alerts dan Tunnel observability; UI akun dapat berbeda, bukan klaim seluruh langkah sudah diklik pada sesi ini.

6. Batas privasi dan tindak lanjut

Monitor tidak menambah port, database, kredensial Cloudflare, atau SaaS baru. State hanya menyimpan field allowlist. Tidak menyimpan nama, IP, username, password, token, isi formulir, URL/query, exception mentah, atau stack trace. UUID akun tetap data pengenal; akses dibatasi operator sudo.

Monitor di VPS yang sama tidak dapat mengirim alert ketika VPS mati total. Tidak ada janji semua error otomatis masuk email. Notifikasi Cloudflare melengkapi laporan lokal, bukan menggantikan pemeriksaan aplikasi/backup.

Tahap berikutnya: review kode dan hasil tes, lewati quality/CI, siapkan SHA serta image immutable, minta persetujuan rilis produksi, deploy backend/frontend melalui alur resmi, lalu validasi event dengan aktivitas operator yang sah. Tidak ada rilis aplikasi atau persetujuan yang dibuat atas nama pemilik.

7. Supabase: klik untuk mencari masalah database

  1. Buka Supabase Dashboard → pilih CMS Sinegasi Picture, cocokkan ref pvbdiftvzoeelibxlxzb.
  2. Klik Logs → Time Range: mulai 15–60 menit sekitar kejadian. Cocokkan zona waktu yang ditampilkan dengan WIB pada laporan VPS.
  3. Pilih Log Type: Postgres untuk DB; PostgREST/API Gateway untuk akses API DB. Saring Level error/warning atau status 5xx sesuai jenis log.
  4. Klik satu baris, catat waktu, SQLSTATE/status dan operasi yang aman. Detail query dapat memuat data privat; jangan menyalin semua log ke chat/PR publik.
  5. Jika kosong, periksa jenis log, waktu dan filter. User filter tidak berlaku pada Postgres dan dapat menyembunyikan hasil. Kosong bukan jaminan sehat.
  6. Buka Advisors → Security Advisor, baca setiap temuan dan remediation. Jangan menjalankan seluruh SQL saran atau mengubah grants/RLS tanpa review.

Login aplikasi kustom bukan otomatis Supabase Auth login; berkas R2 bukan Supabase Storage. Kuota/retensi mengikuti paket, jangan mengekspor semua log atau memasang polling tanpa batas.

Urutan jika ada dugaan kebobolan

  1. Hentikan pengujian. Catat jam WIB, gejala, hostname, request ID/Ray ID dan tindakan yang tidak dikenali; kedua ID berbeda.
  2. Simpan bukti minimum secara privat. HAR/Copy-as-cURL, Console/Network dan log mentah bisa berisi JWT, cookie, nama, URL privat atau request body; jangan unggah ke issue/chat publik.
  3. Dari perangkat bersih, cocokkan seluruh operator/otomasi dan tentukan cakupan akun/endpoint/kredensial terdampak; gunakan Web Console untuk jalur pemulihan bila perlu.
  4. Containment sempit bersama operator: cabut akses/sesi terdampak dan rotasi rahasia yang diduga bocor setelah jalur akses aman. Logout UI saja bukan jaminan token lama dicabut; ikuti mekanisme autentikasi kustom aplikasi.
  5. Jangan reset/reboot VPS, hapus log atau restore DB produksi spontan. Pertahankan backup baik. Snapshot/forensik tambahan perlu tinjau dampak/biaya dahulu.
  6. Perbaiki akar sebab lewat PR + tes regresi, deploy terkontrol dan retest. Ganti password saja tidak membuktikan server sudah bersih.

9. Pengujian keamanan aplikasi yang sudah live

Pentest aktif produksi belum dijalankan. Guide bukan izin scanner otomatis. Kepemilikan domain tidak memberi izin menguji infrastruktur bersama provider. Tidak ada alat baru dipasang atau paket dibeli.

A. Pemeriksaan ringan di Terminal Mac, bukan pentest lengkap

Jalankan satu per satu, sekali saja, tanpa password/token/loop. Ini petunjuk operator, bukan hasil pemeriksaan live pada sesi ini:

curl --proto '=https' --connect-timeout 5 --max-time 10 --max-filesize 65536 --silent --show-error --output /dev/null --write-out 'Health HTTP=%{http_code}\n' https://api.sinegasi.pictures/api/health

curl --proto '=https' --connect-timeout 5 --max-time 10 --max-filesize 65536 --silent --show-error --output /dev/null --write-out 'Tanpa sesi HTTP=%{http_code}\n' https://api.sinegasi.pictures/api/auth/me

Health biasanya 200 (liveness). Endpoint privat tanpa sesi biasanya menolak 401 dari API. Jika Cloudflare menolak 403, backend belum teruji. Jika mendapat 200 pada endpoint privat, berhenti dan minta programmer memeriksa kontrak/respons secara privat; status saja belum membuktikan kebocoran. Jangan menambah -k, mengikuti redirect asing atau mencoba ulang saat 429/5xx.

Untuk melihat header frontend tanpa menampilkan cookie:

curl --proto '=https' --head --connect-timeout 5 --max-time 10 --silent --show-error https://sinegasi.pictures/ |
  awk 'tolower($0) ~ /^(http\/|content-security-policy:|strict-transport-security:|x-content-type-options:|x-frame-options:|referrer-policy:)/ { print }'

Header hilang adalah bahan review, bukan otomatis celah. Misalnya CSP frame-ancestors dapat melindungi framing tanpa X-Frame-Options. Pemeriksaan ringan ini tidak menemukan seluruh SQL injection/IDOR/XSS.

B. Akun uji A/B: hanya skenario yang disepakati

  1. Siapkan dua akun uji milik Anda dan data sintetis tanpa siswa asli, lewat alur admin sah setelah izin dan rencana cleanup; pembuatan akun/data bukan read-only.
  2. Gunakan dua profil Chrome, atau jendela biasa + Incognito. Dua jendela Incognito berbagi sesi, bukan dua akun terisolasi.
  3. Login A, buka satu data dummy yang memang privat milik A. Catat rute dan request ID aman, bukan token. Data yang dibagi ke semua anggota bukan sasaran ownership yang tepat.
  4. Login B, lakukan satu akses baca yang disepakati ke dummy A. Tidak boleh menerima field/berkas privat A. Detail dapat menolak 403/404; daftar dapat benar bila hasilnya terfilter kosong. Jangan mencoba ID acak milik siswa.
  5. Periksa respons API, bukan hanya menu tersembunyi. Rute SPA mengembalikan HTML 200 bukan otomatis kebocoran. Write/delete, ubah role, dan IDOR luas harus di staging.
  6. Jika dummy privat muncul, berhenti pada bukti minimum. Simpan waktu, peran A/B, rute, harapan dan hasil aktual secara privat; jangan mengunduh tabel lain.

Setelah monitoring baru dirilis, satu login/aktivitas sah bisa memeriksa event. Jangan sengaja membuat crash, 500 atau brute force untuk menampilkan log.

C. Pentest aktif: staging terisolasi dahulu

SQL injection, XSS, fuzzing, write/delete/IDOR luas dan uji limiter dilakukan pada salinan kode dengan DB/bucket dummy terpisah, tanpa credential/koneksi produksi atau worker/email nyata. DEV yang masih memakai data produksi bukan staging aman. Jangan membuat branch Supabase berbayar atau menyalin data siswa untuk tes ini.

D. Daftar persetujuan sebelum pentest produksi

  • Host/rute yang boleh dan yang dikecualikan, akun/data dummy, operator, jam mulai–akhir WIB dan kontak penghentian tes.
  • Laju/jumlah request total disepakati. Usulan awal manual: satu request tiap ≥2 detik, satu proses, total kecil yang disetujui; bukan izin provider atau jaminan bebas gangguan. Tidak menjalankan tes bersamaan deployment.
  • Monitor, backup terbaru, pemahaman uji restore dan recovery siap.
  • Stop pada lockout, 429, 5xx/timeout baru, resource melonjak, data non-dummy, perubahan tak diharapkan atau permintaan provider. Jangan pindah IP untuk melewati blok.

Cloudflare: target harus aset sendiri, laju dibatasi; scan mendeteksi tanpa eksploitasi. Pentest mempunyai prasyarat WAF tertentu yang belum tentu tersedia di Free; konfirmasi kesiapan, jangan mematikan proxy/WAF atau membeli paket otomatis. Kebijakan resmi.

Supabase: hanya komponen project sendiri yang diizinkan; DoS, flooding dan serangan project pihak lain dilarang. Kebijakan resmi.

Sumopod: izin pentest publik untuk VPS ini belum terverifikasi; periksa Terms/AUP dan minta konfirmasi jika tidak jelas. Pemeriksaan laporan lokal tetap dapat dilakukan sambil menunggu izin tes aktif.

Metodologi: OWASP WSTG · ZAP Modes · ZAP Baseline.

10. PR/CI: klik mana dan kapan produksi berubah?

  1. Buka repository → Pull requests → pilih PR monitoring → Files changed. Review perubahan, jangan menempelkan password atau bukti insiden privat pada PR publik.
  2. Klik Checks → Code Quality → backend-quality/frontend-quality. Hijau berarti job lulus, bukan produksi sudah berubah; kuning/abu-abu masih berjalan/menunggu.
  3. Alternatif Actions → Code Quality → run branch/SHA PR terbaru → Jobs → langkah gagal. Catat nama test/file dan error aman. Jangan menekan Re-run terus-menerus tanpa diagnosis.
  4. Perbaiki source + tes regresi, push commit baru, lalu cocokkan Checks dengan SHA terbaru. Jangan membaca hasil commit lama sebagai hasil terbaru.
  5. Merge bukan langkah monitoring harian. Perlu persetujuan terpisah; jangan bypass branch protection, mengubah secret atau menyalakan auto-deploy.
  6. Backend resmi memakai Build or Deploy Approved Production Backend: build dan deploy terpisah, mengikat SHA main, evidence, image immutable dan approval baru. Jangan mengisi checksum sembarang atau memakai approval lama; persiapannya dilakukan operator rilis.
  7. Frontend Pages juga harus mengikuti persetujuan rilisnya. Reporter browser memerlukan frontend dan endpoint backend yang cocok sudah terdeploy.
  8. Setelah rilis: satu aktivitas akun uji sah → tunggu collector → lihat event, cek fungsi penting/error/resource; rollback terkontrol jika regresi kritis.

PR juga memperbaiki cursor collector setelah gagal baca serta bucket route. Perbaikan tambahan ini belum otomatis dipasang ke VPS; upgrade collector terpisah dari rilis aplikasi dan tidak perlu mengubah cron backup.
